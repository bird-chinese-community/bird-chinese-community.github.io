---
title: 检查配置
description: 用 birdcc lint 检查 BIRD 2 与 BIRD 3 配置文件，读懂诊断输出，并让 CI 任务在出现问题时失败。
---

`birdcc lint` 用 `@birdcc/linter` 的 32 条 lint 规则 (lint rule) 检查 BIRD 配置。它会跟随 `include` 语句读取其他文件，也可以把 `bird -p` 报告的错误加入结果。

这个命令来自 `@birdcc/cli` 包，需要 Node.js 22 或更新版本。

```sh
npm install --global @birdcc/cli
```

不做全局安装时，用 `npx @birdcc/cli lint bird.conf` 运行。

## 检查单个文件或整个项目 [#targets]

传入文件路径，检查这个文件：

```sh
birdcc lint bird.conf
```

birdcc 从该文件所在目录或上级目录中最近的 `bird.config.json` 读取设置。

不传文件参数时，birdcc 从当前目录向上查找 `bird.config.json`：

- birdcc 检查 `main` 指定的文件；没有设置 `main` 时检查 `bird.conf`。
- 配置设置了 `workspaces` 时，birdcc 检查每个匹配目录中的 `bird.conf`。
- 找不到配置文件时，命令失败，退出码 (exit status) 为 1。

```sh
birdcc init --write
birdcc lint
```

`birdcc init --write` 探测入口文件 (entry file) 并写出 `bird.config.json`。[项目配置](../configuration/entries-and-includes.mdx)介绍这个文件，[`init` 参考](../cli.mdx#init)列出探测选项。

## 跨文件分析 (cross-file analysis) [#cross-file]

跨文件分析默认开启。birdcc 分析入口文件的 include 图 (include graph)，即入口文件以及它直接或间接 include 的全部文件。

- 含有 `include` 语句的文件就是入口文件。
- 对其他文件，birdcc 在文件所在目录及最多四层上级目录中探测入口文件。探测不到入口文件时，以该文件本身作为入口文件。
- 输出包含 include 图中每个文件的诊断 (diagnostic)。

示例项目：

<Files>
  <Folder name="project" defaultOpen>
    <File name="bird.config.json" />
    <File name="bird.conf" />
    <File name="filters.conf" />
    <Folder name="old" defaultOpen>
      <File name="legacy.conf" />
    </Folder>
  </Folder>
</Files>

```bird2 title="bird.conf"
router id 192.0.2.1;
include "filters.conf";

protocol device {
}

protocol bgp upstream {
  local as 65000;
  neighbor 192.0.2.2 as 65001;
  ipv4 {
    import filter peer_in;
    export filter peer_out;
  };
}
```

`filters.conf` 定义了 `peer_in`，没有文件定义 `peer_out`。检查 `filters.conf` 时，birdcc 分析 `bird.conf` 的 include 图，并报告 `bird.conf` 中的问题：

```sh
birdcc lint filters.conf
```

```text
WARNING sym/filter-required [file:///srv/bird/project/bird.conf] 12:19 Protocol 'upstream' references unknown filter 'peer_out'
```

`old/legacy.conf` 不在 `bird.conf` 的 include 图中。检查 `old/legacy.conf` 时，birdcc 同样分析 `bird.conf` 的 include 图，所以输出中没有 `old/legacy.conf` 的诊断。用 `--no-cross-file` 单独检查这个文件：

```sh
birdcc lint old/legacy.conf --no-cross-file
```

```text
WARNING sym/duplicate [file:///srv/bird/project/old/legacy.conf] 2:8 [semantic/duplicate-definition] define 'LEGACY_ASN' is already defined
```

在 `bird.config.json` 中写 `"crossFile": { "enabled": false }`，每次运行都会关闭跨文件分析。

include 图有以下上限：

- 嵌套 16 层
- 256 个文件
- 单个文件 2 MiB
- 总计 16 MiB

`--include-max-depth` 与 `--include-max-files` 只修改本次运行的前两项上限。[`crossFile` 配置项](../configuration/reference.mdx#cross-file)可以修改全部四项。

birdcc 跳过超过上限的 include，并报告 `sym/undefined`。所检查的文件本身超过大小上限时，命令失败。

include 解析到工作区根目录 (workspace root) 之外时，birdcc 同样跳过它并报告为 `sym/undefined`，除非 `crossFile.externalIncludes` 为 `true`。[include 解析](../configuration/entries-and-includes.mdx#include-resolution)说明查找顺序与工作区根目录。

## 读懂输出 [#output]

每条诊断占一行，依次包含：

1. 级别 (severity)
2. 规则代码 (rule code)
3. 文件 URI
4. 行号与列号，都从 1 开始
5. 消息

```text
WARNING sym/filter-required [file:///srv/bird/project/bird.conf] 12:19 Protocol 'upstream' references unknown filter 'peer_out'
```

- 没有诊断时，命令输出 `No problems found during linting`。
- 解析器 (parser) 与 `@birdcc/core` 用自己的代码报告一部分问题。birdcc 把这些诊断归到规则代码下，并在消息开头的方括号中保留原始代码，例如 `[semantic/duplicate-definition]`。在 `linter.rules` 中使用规则代码。
- 来自 `bird -p` 的诊断没有文件 URI。
- `-v` 把进度与耗时输出到 stderr，每行以 `[verbose]` 开头。

[lint 规则](./rules.mdx)列出每个规则代码及其报告的问题。

## 级别与退出码 [#exit-status]

`sym`、`cfg`、`net`、`type` 规则默认报告 `warning`，`bgp` 与 `ospf` 规则默认报告 `info`。

| 结果                                                                                        | 退出码 |
| ------------------------------------------------------------------------------------------- | ------ |
| 至少一条诊断的级别为 `error`                                                                | 1      |
| 全部诊断为 `warning` 或 `info`，或者没有诊断                                                | 0      |
| 命令失败：没有目标文件、文件无法读取、`bird.config.json` 无效、选项值无效、文件超过大小上限 | 1      |

在默认级别下，即使存在语法错误，`birdcc lint` 的退出码也是 0，因为 `cfg/syntax-error` 报告 `warning`。所有命令的[退出码](../cli.mdx#exit-codes)见 CLI 参考。

## 让 CI 在出现问题时失败 [#fail-on-findings]

要让 CI 任务在出现 lint 问题时失败，在 `bird.config.json` 中把规则组提升到 `error`：

```json title="bird.config.json"
{
  "$schema": "https://raw.githubusercontent.com/bird-chinese-community/BIRD-LSP/main/schemas/bird.config.schema.json",
  "main": "bird.conf",
  "linter": {
    "rules": {
      "sym/*": "error",
      "cfg/*": "error",
      "net/*": "error",
      "type/*": "error"
    }
  }
}
```

使用这份配置时，示例项目输出下面一行，`birdcc lint` 的退出码为 1：

```text
ERROR sym/filter-required [file:///srv/bird/project/bird.conf] 12:19 Protocol 'upstream' references unknown filter 'peer_out'
```

要让 BGP 与 OSPF 问题也导致失败，再加上 `"bgp/*": "error"` 与 `"ospf/*": "error"`。[修改级别](./rules.mdx#severity)说明 birdcc 如何匹配这些键。

[CI](../ci/github-actions.mdx) 给出完整的 GitHub Actions 工作流 (workflow)。

## 用 bird -p 检查 [#bird]

```sh
birdcc lint bird.conf --bird
```

`--bird` 在静态分析 (static analysis) 之后运行校验命令 (validation command)，并把校验命令报告的错误加入输出。在 `bird.config.json` 中写 `"linter": { "withBird": true }`，每次运行都会进行校验。

birdcc 按下列顺序选用第一个可用的命令模板 (command template)：

1. `--validate-command` 选项。
2. `bird.config.json` 中的 `bird.validateCommand`。
3. `bird.config.json` 中的 `bird.binaryPath`，生成 `<binaryPath> -p -c {file}`。
4. 环境变量 `BIRD_BIN`，生成 `"<BIRD_BIN>" -p -c {file}`。
5. `bird -p -c {file}`。

```sh
BIRD_BIN=/usr/sbin/bird birdcc lint bird.conf --bird
birdcc lint bird.conf --bird --validate-command "/usr/sbin/bird -p -c {file}"
```

- birdcc 把 `{file}` 替换为所检查文件的绝对路径。模板中没有 `{file}` 时，birdcc 把路径追加到末尾。
- birdcc 不经过 shell 运行命令，工作目录为所检查文件所在目录，超时时间为 10 秒。使用 `workspaces` 时，birdcc 为每个所检查的文件运行一次命令。
- 在容器或其他主机上运行 BIRD 的模板，必须能在相同的绝对路径找到该文件。
- 命令写到 stderr 的每一行都会成为一条 `bird/parse-error` 诊断。命令无法启动、超时，或以非零状态退出且 stderr 没有输出时，产生 `bird/runner-error`。这两个代码的级别都是 `error`，所以会让命令以退出码 1 结束。

CLI 参考中的 [BIRD 校验](../cli.mdx#bird-validation)一节列出支持的 stderr 格式。

## JSON 输出 [#json]

```sh
birdcc lint --format json > birdcc-lint.json
```

`--json` 等同于 `--format json`。退出码与文本输出相同。

报告包含 `diagnostics` 数组，以及计数 `files`、`rules`、`errors`、`warnings`。[JSON 输出](../cli.mdx#json-output)列出全部字段。
